# Админка — gap-анализ онбординга и редактирования каталога

**Дата**: 2026-04-20
**Время**: 22:23 UTC (2026-04-19)
**Ветка**: `feature/engine-v4`
**Статус**: ✅ **MOSTLY DONE 2026-04-19/21** — Onboarding MVP shipped: `b8adcd1` (CSV + Shopify integrations), `ef280aa` (full auth stack — OAuth/2FA/sessions/workspaces/invites). Catalog editing gaps закрыты дизайном `admin_catalog_design_2026-04-23.md` — имплементация впереди. Этот документ оставлен как исторический инвентарь gap'ов на момент 2026-04-19.
**Контекст**: клиент хочет максимально лёгкий путь загрузки и редактирования собственного каталога — как для первого подключения, так и для ежедневного обогащения. Цель этой доки — зафиксировать что уже есть в админке сегодня и чего не хватает, чтобы на следующем шаге прицельно спроектировать магический путь.

---

## TL;DR

Сегодняшняя админка — это **JSON-import + ручной CRUD + файловый enrichment**. Для клиента это значит: «экспортируй каталог в наш формат JSON → залей файл → жди». Это работает для нас внутри (heybabescosmetics, 967 SKU), но плохо работает как продукт, потому что:

1. Нет пути от «у меня есть сайт» к «продукты в чате» без ручной перегонки данных.
2. Нет синхронизации — импорт одноразовый, цены/остатки протухают.
3. Схема полей зашита в `ImportItem` — любой нестандартный атрибут идёт в `attributes` map и не попадает в поиск/виджеты без ручной работы с пресетами.
4. Нет видимости качества — клиент не знает какие продукты «плохие» и какие запросы его каталог не закрывает.
5. Нет bulk-операций и rollback — редактирование = клик-клик по одному.

**Главный блокер** для масштабирования онбординга — **отсутствие магического пути входа**. Сейчас любой новый клиент = ручной проект (crawler под его сайт + enrichment + проверка).

## 2. Что не хватает (gap-инвентарь)

Группировка по темам. Внутри каждой темы — gap'ы отсортированы по важности для онбординга нового клиента.

### 2.1. Источники данных (input surface)

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет CSV/Excel импорта** | Только JSON в нашем формате. | 90% клиентов выгружают каталог в CSV/XLSX из Shopify/1C/InSales. |
| **Нет коннекторов к e-commerce платформам** | Shopify / WooCommerce / InSales / Tilda / Bitrix — OAuth + sync. | Убирает этап «экспортируй → сконвертируй → загрузи» полностью. Магический путь требует хотя бы одного коннектора. |
| **Crawler не интегрирован в UI** | `cmd/crawler/` запускается руками разработчиком. | Клиент не может сказать «вот мой сайт» и получить каталог. |
| **Нет мапинга колонок** | Если и будет CSV — неясно как `cena`/`preis`/`amount` → `price`. | Без этого каждый клиент = ручной проект. |
| **Нет Google Sheets sync** | — | Самый простой способ для маленьких клиентов вести каталог. |
| **Нет webhook-приёма** | Клиент не может пушить изменения. | Только pull, только мы опрашиваем — значит нужна наша инфра cron'ов. |

### 2.2. Синхронизация и свежесть

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Импорт одноразовый** | Нет cron/webhook для периодического обновления. | Цены, остатки, новые SKU протухают за дни. Каталог деградирует без внимания. |
| **Нет diff-импорта** | Каждая заливка — full replace (upsert по SKU). Нет отчёта «добавилось 12, обновилось 340, удалено 5». | Клиент не видит что изменилось, не может откатить. |
| **Нет rollback** | Залил кривой файл — каталог в кривом состоянии. | Страх перед кнопкой «импортировать». |
| **Нет версионирования** | Нет истории «этот продукт был таким 3 дня назад». | Нельзя аудитить, нельзя откатить точечно. |

### 2.3. Схема полей и per-tenant кастомизация

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Схема `ImportItem` зашита в код** | sku/name/brand/category/price/… + `attributes: map[string]any` как свалка для всего остального. | Косметике нужен `skin_type`, электронике — `wattage`, фарме — `dosage`. Сейчас всё это летит в `attributes` и не попадает в слоты виджетов. |
| **Нет `catalog.field_definitions`** | (Это волна B7 из `PRE_LAUNCH_TASKS.md`.) Тенант не может определить свою схему. | Без этого пресеты и поиск остаются cosmetics-specific. |
| **Нет role-based slot resolution** | Пресеты используют `fieldName: images/name/price/...` hardcoded. | Клиент не может сказать «вот это поле у меня = заголовок карточки». |
| **Нет UI для схемы** | Даже если backend научится — нет экрана «определи свои поля». | Клиент не сможет воспользоваться. |

### 2.4. Медиа и мультимодальный вход

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Голосовуха → текст** | Нет приёмника аудио, нет Whisper-пайплайна. | Юзер-кейс из твоего сообщения: клиент хочет загрузить голосовую историю про продукт. |
| **PDF-спеки → атрибуты** | Нет парсера PDF. | У электроники/мебели часто только PDF-datasheet. |
| **Картинка → структура** | Нет OCR (фото упаковки → состав, фото ценника → цена). | Быстрый путь добавить продукт с телефона. |
| **Видео → кадры/транскрипт** | — | Для beauty/fashion/DIY часто основной контент. |
| **Нет общего enrichment-queue** | Enrichment сейчас «файл → файл». Нет очереди задач per-product. | Всё вышеперечисленное хочется сложить в одну очередь задач. |

### 2.5. Качество данных и observability

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет data quality dashboard** | Нет экрана «40% продуктов без изображения», «120 SKU без описания», «70 продуктов с одинаковым названием». | Клиент не знает что чинить. |
| **Нет «0-result queries»** | Мы не показываем какие запросы чат не смог обслужить. | Прямой сигнал «добавь эти продукты/синонимы». |
| **Нет поиска по дубликатам** | — | После двух-трёх импортов каталог зарастает дублями. |
| **Нет search-analytics** | Что ищут, что находят, куда кликают. | Бизнесовый feedback loop. |
| **Нет enrichment-отчёта per tenant** | Глобальный `current` job, нет per-product истории «этот SKU обогащался 3 раза, стоимость X центов». | Клиент не видит что с его данными делает AI. |

### 2.6. Редактирование и массовые операции

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет bulk-edit** | Только по одному продукту. | 5-50k SKU руками не отредактируешь. |
| **Нет bulk-enrichment по фильтру** | «Обогатить все продукты в категории X». | Всё enrichment — пофайлово. |
| **Нет inline-редактирования списка** | Каждое изменение = переход в detail page. | Медленно. |
| **Нет массового импорта изображений** | — | ZIP с картинками по SKU — типовой кейс. |
| **Нет тегирования/категоризации в батче** | — | — |

### 2.7. Превью и безопасность редактирования

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет preview «как будет в чате»** | Клиент правит продукт и не видит результат до публикации. | Снимает страх, ускоряет итерации. |
| **Нет draft/publish** | Всё, что сохранилось, сразу видно в чате. | Нельзя подготовить релиз. |
| **Нет staging каталога** | Нельзя проверить изменения перед выкаткой. | — |
| **Нет audit log** | Кто что когда поменял. | Важно для клиентов с несколькими операторами. |

### 2.8. Контент-генерация

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет генерации описаний** | Клиент с голыми названиями и ценами не может быстро стартовать. | Магический путь = «дай мне минимум, остальное сгенерим». |
| **Нет перевода** | Каталог на одном языке, а чат — мультиязычный. | Нужно для любого международного клиента. |
| **Нет SEO/атрибут-генерации** | LLM может достать `color`, `material`, `size` из описания, но UI этого не предлагает. | — |
| **Нет синонимов/алиасов** | «помада / lipstick / lip color» — сейчас только если в тексте. | Ключевой фактор качества поиска. |

### 2.9. Онбординг как поток

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет wizard'а первого запуска** | После логина клиент упирается в пустую админку. | Нет «первой победы» — клиент уходит. |
| **Нет vertical-templates** | Косметика / электроника / fashion / food — нет стартовых схем и пресетов. | Каждый клиент = настройка с нуля. |
| **Нет sandbox-демо** | Клиент не может попробовать «чат на моём каталоге» до заливки. | Мешает sales-конверсии. |
| **Нет health-score онбординга** | Нет индикатора «твой каталог готов на 60%». | Клиент не знает куда двигаться. |

### 2.10. Многопользовательская админка (для самого клиента)

| Gap | Что значит | Почему важно |
|-----|-----------|--------------|
| **Нет ролей и прав** | Один логин на тенанта. | Большой клиент = команда: контент-менеджер, админ, маркетолог. |
| **Нет инвайтов** | — | Блокер для организаций >1 человек. |
| **Нет team-activity** | — | — |

## 3. Варианты магического пути (кратко, для следующего шага)

Это не план, это **меню**. На следующем шаге выберем 1-2 и спроектируем детально.

### A. «Paste URL» — crawler-first

Клиент вставляет URL своего сайта → наш crawler (`cmd/crawler/`) парсит JSON-LD + schema.org → enrichment через Haiku → каталог готов.

- **Плюсы**: нулевое трение. Клиент ничего не экспортирует.
- **Минусы**: работает только на сайтах с нормальной разметкой. Для самописных сайтов — 50/50.
- **Что надо**: интегрировать crawler в backend как usecase (не CLI), добавить UI с прогрессом, переиспользовать enrichment.
- **Срок**: ~1-2 недели.

### B. «Connect Shopify» — OAuth-коннектор

Клиент нажимает «подключить Shopify» → OAuth → мы тянем `/admin/api/products.json` → sync каждые N часов.

- **Плюсы**: это 30-40% рынка SaaS e-com. Свежесть из коробки.
- **Минусы**: надо быть в Shopify App Store либо крутить private apps. Работает только для Shopify.
- **Что надо**: OAuth app, маппер Shopify product → наш `ImportItem`, cron для sync, webhook handler для real-time.
- **Срок**: ~2-3 недели (+ App Store review, если публично).

### C. «CSV с AI-мапингом» — универсальный но не магический

Клиент грузит CSV → LLM смотрит на хедеры + первые 5 строк → предлагает mapping → клиент правит → импорт.

- **Плюсы**: работает **для всех** форматов, включая exотические.
- **Минусы**: всё равно требует шагов от клиента. Не магия.
- **Что надо**: CSV-парсер, mapping-UI, LLM-prompt для предложения мапинга, + всё то же что для JSON.
- **Срок**: ~1 неделя.

### D. «Опиши что продаёшь» — AI-generated starter

Клиент пишет 2-3 предложения → LLM генерит: схему полей, категории, 5-10 стартовых продуктов, пресеты. Клиент валидирует.

- **Плюсы**: максимум магии. Показывает ценность до заливки.
- **Минусы**: это демо/sandbox, не боевой каталог. Требует отдельной интеграции с настоящим каталогом потом.
- **Срок**: ~1 неделя для sandbox.

### E. Комбо A+D

URL → crawler тянет что может → для недостающих полей LLM достраивает из описаний → клиент видит готовый preview за 10 минут и либо подтверждает, либо правит.

- **Плюсы**: покрывает и разметкой богатые, и скудные сайты. Максимальная вероятность «работает с первого раза».
- **Минусы**: сложнее в реализации, больше edge-cases.
- **Срок**: ~3 недели.

## 4. Моя рекомендация к следующему шагу

**Вариант E (URL + AI-достройка)** как основной магический путь, с **вариантом C (CSV с мапингом)** как honest fallback для клиентов чей сайт непригоден для парсинга.

**Почему E, а не B (Shopify)**:

- B зависит от платформы и её процесса апрува — может ждать недели.
- E работает для **любого** клиента с сайтом, независимо от стека. Это включает российский рынок (1C/Bitrix/InSales), где Shopify не массовый.
- Crawler уже есть в коде — это база. Enrichment уже есть — это вторая база. Надо соединить их в flow.

**Минимальный MVP магического пути (что я бы проектировал на следующем шаге)**:

1. `POST /admin/api/v1/onboarding/start {url}` → создаёт Onboarding-job.
2. Job: crawl → normalize → enrich → проверка на gaps → preview.
3. UI: progress-bar с живыми апдейтами, preview таблица, кнопка «опубликовать / показать в чате».
4. Fallback: «сайт не парсится» → предложить CSV upload с AI-мапингом.

Открытые вопросы для обсуждения на следующем шаге:
- Домены приёмки: только наш crawler или интеграция с 3rd-party (Apify, ScrapingBee) для сложных сайтов?
- Enrichment-cap: сколько тратим на клиента до того как он заплатит? (Haiku всё равно ~$1-2 за 967 продуктов, терпимо.)
- Как связать `Onboarding-job` с будущей периодической sync'ом — чтобы не писать два разных пайплайна.

## 5. Что этот документ **не покрывает**

- Детальный дизайн магического пути — это следующий doc.
- Приоритизацию всех 10 gap-тем после MVP — отдельная задача, зависит от первых клиентов.
- B7 (`catalog.field_definitions`) — описан в `PRE_LAUNCH_TASKS.md` и `sales_readiness_assessment_2026-04-12.md`. Магический путь должен быть спроектирован так, чтобы **не мешать** B7 когда он приземлится (например, схема полей должна быть расширяемой с первого дня, даже если на старте hardcoded).
