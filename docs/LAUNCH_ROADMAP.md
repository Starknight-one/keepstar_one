## 1. Что за продукт и какую боль он решает

**Keepstar One Ultra** — AI-powered SaaS B2B2C чат-виджет для e-commerce.

**Боль на рынке.** Самый дорогой сегмент в e-commerce — **discovery**: момент когда покупатель ещё не знает чего хочет. Существующие решения (плоский каталог + поиск + текстовые чатботы) плохо конвертят, потому что покупка — это **визуальный акт**, а текстовый ответ его не закрывает. Сделать визуального AI-ассистента самому — это команда фронтов/бэков/LLM/дизайнера. SMB и middle-market магазины не потянут.

**Что делаем.** Магазин вставляет один `<script>` на сайт — получает ассистента, который вместо текста собирает **визуальные ответы**: карточки товаров, галереи, сравнения, детали, баннеры. В одной чат-сессии пользователь скачет «покажи 5 помад» → «сравни эти две» → «расскажи про состав» → «в корзину», и каждый ответ — это новая собранная UI-композиция, не текст.

**Архитектура продукта.**
```
Юзер → Chat Widget (script tag, Shadow DOM)
         ↓ REST
       Chat Backend (V4 engine, на Railway)
         ↓
    Agent1 (NLU) → catalog_search / state_filter / history_lookup
    Agent2 (Render) → visual_assembly tool (ops + presets)
         ↓
    Formation JSON → Widget рендерит
```

**Moat — двухагентная архитектура.** Agent1 разбирается с интентом и достаёт правильные данные; Agent2 решает как это **показать**. Эта разделённость даёт одновременно правильность (данные из реального каталога) и красоту (визуал, который мерчант не стыдится встроить).

**Почему «не MVP, а полноценный продукт сразу».** Три гейта запуска, и каждый дорого ошибиться:
1. **Self-serve onboarding** — мерчант должен за 3 минуты подключить магазин и увидеть работающий виджет. Иначе не покупает.
2. **Качество данных в каталоге** — если ассистент путает цены/состав/категории, мерчант черно-листится после первой жалобы клиента.
3. **Качество визуала** — если виджет выглядит дёшево, мерчант не повесит его на свой сайт.

### 4.3. Эксперты — концептуальная ошибка в текущей структуре

**Ошибка.** У нас сейчас 9 экспертов по горизонтальным слоям гексагона: `backend-domain`, `backend-ports`, `backend-adapters`, `backend-usecases`, `backend-handlers`, `backend-pipeline`, `frontend-shared`, `frontend-entities`, `frontend-features`. Каждый эксперт — это слайс одного слоя через **все** домены. Поэтому:
- YAML'ы пухнут (мешают концерны)
- Когда работа над одной фичей — приходится дёргать 6 экспертов сразу
- Self-improve работает плохо

**Правильно.** Оригинальная концепция (Бэдкок) — эксперты по **вертикальным доменам**: Database, WebSocket, Billing, Security. Каждый покрывает домен через все слои гексагона. YAML до 1000 строк — норма, больше — значит сам модуль раздут и нужен рефакторинг.

**План перестройки экспертов** (фаза 2):

| `catalog` | postgres_catalog, harvester, discovery, apply/revert, master_products, tier2, V4-чат-чтение каталога |
| `engine-v4` | domain (Atom/Widget/Formation), engine_v4 package, ops, presets, binding, constraints, visual_assembly tool |
| `pipeline-agents` | Agent1/Agent2 промпты, pipeline_execute, tool execution, span tracing, prompt caching |

«Интеграция v9» = три проекта в одном:
1. Заменить канвас в админке на v9-ный

Каждый проект ≈ размер всего рефакторинга каталога. **Vlad потратил ~1.5 месяца только на то чтобы V4 работал быстро/дёшево/качественно.** После v9-интеграции потребуется похожий период пост-стабилизации.
