Catalog — таблицы, колонки, связи

Целевое состояние ПОСЛЕ Group D. Каждая таблица показана с ключевыми колонками, PK/FK, скоупом (shared / per-tenant) и парой сэмпл-рядов. Связи вложены — дочерние таблицы под родителями, M:N через junction-таблицы помечены. Полный реестр кросс-ссылок внизу.

Источник правды о продукте. Один master = одна семья. Один на всех тенантов. Slow churn, rich data, ingest-time-heavy.

Сквозной сценарий: «лореаль тушь 7мл» в чате Beauty Boutique V5 chat делает запрос к tenant_search_projection WHERE tenant_id = t1, ORDER BY embedding ↔ query_vector LIMIT 10. HNSW в slice'е Beauty Boutique находит строку (t1, var-7). JOIN в read-path: projection (поиск) → catalog.products (price, display_name, tenant_overrides) → master_products (canonical name/brand, embedding не используется) → master_variants (volume_ml=7, axes) → master_cosmetics (skin_type, key_ingredients). Render: карточка показывает display_name="L'Oreal Mascara Volume Million", price=$25, badges=[HIT, curator-picked], variant_picker={7ml selected, 12ml available because Beauty Boutique listing-row для var-12 тоже существует}. У Skincare Pro (t2) — тот же поиск находит ТОЛЬКО var-7 (потому что для var-12 listing-строки нет, projection её не содержит). Picker показывает 7ml selected, 12ml unavailable.
