## What "variant = listing" means here (Position B, default-variant flavor)
Every `catalog.products` row (a tenant's listing) references a `master_variant`. A simple product
(no real variants) gets exactly one synthetic `variant_kind='default'` variant. So: 1 master ↔ 1
default variant ↔ 1 listing per tenant. Recognizing *real* siblings (one product sold as 7ml + 12ml
= one master with N variants) is the genuinely agentic grouping and stays deferred.

## Changes
**Migration (`catalog_migrations.go`, D1b block after D4):**
1. Add `'default'` to the `master_variants.variant_kind` CHECK (was `real/addon/bundle`) — finds the
   real constraint name via `pg_constraint` first, so it works regardless of how it was created.
2. Partial unique index `idx_catalog_mv_one_default (master_product_id) WHERE variant_kind='default'`
   — at most one default per master; also the `ON CONFLICT` arbiter.
3. **34 orphan listings** (legacy Shopify rows with `master_product_id` NULL, no variant — real
   K-beauty products) → synthesize a master each (`sku='legacy-orphan-<id>'`, name from listing),
   link. No data loss.
4. Default variant for every master without one.
5. Bind every listing to its master's variant (prefer default).
6. `ALTER ... master_variant_id SET NOT NULL`. All steps idempotent.

**apply (`catalog_v2_writer_adapter.go`):**
- `UpsertListing`: ensure the master has a default variant (idempotent CTE), bind the listing to it;
  added `master_variant_id` to the INSERT + `ON CONFLICT` (`COALESCE(existing, excluded)` so a real
  variant link is never clobbered by a default).
- `BulkUpsertListing`: a batched ensure-defaults statement first, then the bulk listing INSERT
  resolves `master_variant_id` per row (no N+1).

**domain (`master_variant.go`):** added `VariantKindDefault = "default"` + doc note (default is
treated like real for search; only addon/bundle are excluded).
