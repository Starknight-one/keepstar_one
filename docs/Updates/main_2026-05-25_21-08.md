# Group D Phase 1 — D4: stock consolidation (Target A) — 2026-05-25 (Alpha 0.9.8)

## Context
Continuing the Group D remaining-work plan. Prior shipped: Alpha 0.9.6 (item 1 dead services +
item 2 tier2-canonical), Alpha 0.9.7 (Task #7 dead cosmetics code + D3 categories → V2). This
session: **D4 — single-source the tenant commercial data (stock).**

**A design decision changed the plan.** The original D4 row said "`catalog.stock` is canonical;
fix curator's stale read + drop the `products.stock_quantity` denorm." Owner raised: stock AND
price are both **tenant-specific listing facts** (same product, two merchants = different stock
and price), so D4 should treat them uniformly, not just patch stock. We dug into the live code and
found three things that decided it:

1. **`catalog.stock.reserved` is a dead column** — defined at `catalog_migrations.go:70`, read/
   written nowhere. No reservation/hold system exists.
2. **Stock is never filtered or sorted** anywhere (admin/V5/curator) — it is display-only. So a
   normalized stock table buys nothing. (Price, by contrast, IS filtered + sorted in V5 —
   `postgres_catalog.go:151,156,250` — so it must stay queryable on the listing row.)
3. **The same writer already split the offer across two tables:** `BulkUpdateStock` wrote stock to
   `catalog.stock` (`catalog_adapter.go:1014`) and price to `catalog.products`
   (`:1033`) in one call — the exact asymmetry that motivated the question.

**Decision — Target A (consolidate onto the listing row).** The "offer" = (price, currency, stock)
for a tenant's listing. Price already lived single-homed on `catalog.products`; we made stock match
by keeping `products.stock_quantity` as the one home and **dropping `catalog.stock` + dead
`reserved`**. A separate hot stock table (the old "future KeyDB/Tarantool" framing) is a
write-throughput optimization we don't need at current volume — and it's a mechanical re-split
per-tenant if throughput ever demands it. Owner's retail experience (40k stores, Tarantool, 20k
ops/sec) is exactly where the split pays off; we're nowhere near that.

## Changes
**Migration (`catalog_migrations.go`):**
- Removed the legacy `catalog.stock` `CREATE TABLE` + `idx_catalog_stock_tenant` + the seed INSERT
  (so the migration converges to the target model without re-creating the table — no oscillation).
- Added a D4 Group-D block: backfill `products.stock_quantity` FROM `catalog.stock` (guarded on
  table existence — `catalog.stock` held the live values, so they win), then
  `DROP TABLE IF EXISTS catalog.stock CASCADE`. Idempotent: post-drop the guard is a no-op.

**Admin adapter (`catalog_adapter.go`):**
- `ListProducts` + `GetProduct`: removed the `LEFT JOIN catalog.stock` and changed
  `COALESCE(st.quantity, p.stock_quantity)` → `p.stock_quantity` (read the column directly).
- `BulkUpdateStock`: rewrote the stock upsert from `INSERT catalog.stock` to
  `UPDATE catalog.products SET stock_quantity` (mirrors the existing price UPDATE). RowsAffected
  semantics unchanged.
- `UpdateProduct` + `UpsertProduct`: removed the now-redundant `catalog.stock` dual-writes (both
  already set `products.stock_quantity` in their main statement).

**Curator:** NO CHANGE. It already read `COALESCE(p.stock_quantity, 0)` (`postgres.go:366,619`);
its "stale read" bug is fixed for free once the column is canonical + the writer keeps it fresh.

**Spec (`CATALOG_GROUP_D_SPEC.md`):** status item 5 → DONE (Target A); locked-decisions note;
D4 detail section + L3 layer table updated to supersede the "`catalog.stock` canonical" framing.
