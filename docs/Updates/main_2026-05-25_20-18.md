## D3 — categories: legacy V1 → target V2 junction model, drop V1
**Finding that inverted the plan's premise:** for the MASTER catalog, V1
(`master_products.category_id` → `catalog.categories`) was the LIVE model (written by import +
enrichment + INSERT/UPDATE, read by all search/filter + a recursive hierarchy CTE, indexed).
The V2 master side (`master_categories` + `master_product_categories`) existed but had **no
writers** (only the discovery digest read the empty junction). So "drop V1" was a real model
migration, not a cleanup. Owner chose: do the full migration now, drop legacy.

- **Migration** (`catalog_migrations.go`, Group D block): backfill `catalog.categories` →
  `master_categories` **reusing the V1 UUIDs** (preserves hierarchy + lets product links map by
  id), backfill `master_product_categories` from `master_products.category_id`, then
  `DROP COLUMN category_id CASCADE` + `DROP TABLE catalog.categories CASCADE`. Guarded on
  `category_id` existence → idempotent. Category `vertical` defaults to `'unknown'` (curator refines).
  Also removed the legacy V1 schema statements (table create, `category_id` column, indexes 58/61/62/146)
  so the migration re-runs cleanly (those index-creates would otherwise error once `category_id` is dropped).
- **Code reroute** (`catalog_adapter.go`): category filter recursive-CTE → junction +
  `master_categories` hierarchy; 7 display JOINs → `LEFT JOIN LATERAL (… LIMIT 1)` on the junction;
  `GetCategories`, `GetOrCreateCategory` (writes `master_categories`, vertical `'unknown'`),
  `GetCategoryBySlug`, `UpsertMasterProduct` (+ junction link), `UpdateMasterProductPIM` (+ junction link),
  `GenerateCatalogDigest`. Also `cmd/seed` (→ `master_categories`) and `cmd/rebuild-embeddings` (junction LATERAL).
- **Server** (`cmd/server/main.go`): bumped startup migration ctx 30s → 120s (Neon cold-start +
  ~170 statements were hitting the 30s deadline).
