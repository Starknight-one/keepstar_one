## Context

Catalog flow was stuck for two weeks on Sephora-CSV ingest. Yesterday's
seed run was the first real measurement on a non-Shopify, non-K-beauty
catalog (8494 rows, 27 fields). Discovery agent burned $0.36 and apply
managed only 29 / 8494 rows — the rest looped through mapping_miss
because (a) `classify_rules` were shopify-shaped (`product_type contains
'Skincare'`) while Sephora has `primary_category`, (b) apply's
`classifyContextFromRaw` extractor was hardcoded to 4 Shopify keys, and
(c) `MatchOrCreateMaster` is immutable on bind so re-encountering the
same SKU loses its incoming enrichment data.

Diagnosis showed four interlocking gaps, not one bug. Owner asked for a
single bundled milestone closing all four, plus a curator UI so the
"new masters land for approval" half of the design becomes real instead
of a TODO.

Business reason: without this, V5 engine work is blocked — there is no
diverse seeded test catalog to develop the chat engine against.

## Known gaps (discovered during the run, NOT closed in this milestone)

1. **Transform tolerance.** Apply's `transform="numeric"` (and friends `int`, `ml_from_string`, `g_from_string`) panic-equivalents on empty input string with `strconv.ParseFloat: parsing "": invalid syntax`. Sephora CSV has many empty `sale_price_usd` / `value_price_usd` / `child_min_price` / `child_max_price` fields — those are not on sale / not variant-priced, which is normal. The result: every row hit a transform-failure mapping_miss; apply triggered narrow discovery 3 times (the cap), then silently failed every remaining row without creating a single master. **Fix is one paragraph** in `internal/usecases/apply_v2_transforms.go` — make numeric transforms return `(nil, nil)` when input is empty/blank instead of erroring. This is the unblocker for the next seed attempt.

2. **Approve doesn't actually mutate `master_products` yet.** Curator UI flips `approval_status='approved'` and `master_pending_changes.status='approved'` correctly. But the actual column writes (e.g. apply approved `skin_type[]` adds → master_products.skin_type) are NOT performed. The pending row is the source-of-truth marker; mutation requires per-field schema routing (master_products vs master_cosmetics vs tier3.<key>) and is the next round's work.

3. **Bulk MatchOrCreateMaster / UpsertCosmetics / MergeTier3.** Listings are bulk now; the other writer paths stayed per-row. At 100 tenants × 10k masters this becomes the bottleneck again. The pattern from `inbox_adapter.go:84-184` and `catalog_v2_writer_adapter.go:140-280` (UNNEST + CTE) is the template — straight followup.

4. **Cron source-side pull.** Currently the cron only re-applies the existing inbox (calls `orchestrator.ManualSync`). True "pull from source" requires async Shopify Bulk Operation polling (the API is asynchronous — submit operation → poll status → download JSONL). The shared infrastructure to do that lives in `ShopifyHarvester` but wiring it into the cron with proper polling + idempotency was deferred.

5. **`apply_v2_test.go` mocks updated for shape only.** Test coverage for the new bind→enrich path (assert EnrichExistingMaster called with expected scalars/arrays, assert MarkApplied only after BulkUpsertListing) is thin. Existing tests pass because the fake records calls — no assertions yet check the new payload.

6. **Pre-existing test failures.** `Scenario_052-055` (Shopify auto-merge consent flow) were red before this milestone and remain red. Out of scope.

## What was specifically NOT done (guardrails honoured)

These were rejected by owner during planning; the milestone respects them:
- No proactive novelty-detection. `mapping_miss` reactive flow is enough.
- No scalar overwrite on bind. Non-empty master.brand stays untouched.
- No row-by-row SQL in new write paths. All UNNEST batch.
- No cross-service import between admin and V5. Copied SQL shape, retargeted tables.
- No tenant-specific code branches in `classifyContextFromRaw`. Artifact-driven only.
- No deletion of `classify_rules` DSL. Kept as fallback after `vertical_aliases`.
- No UI control of cron in v1. Env-var + per-tenant settings toggle.
- No filtering of listings in V5 read-path by master `approval_status`. Listings stay visible per owner's explicit ask.
