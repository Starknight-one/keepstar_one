## What shipped between this update and the previous one

### Alpha 0.9.2 — Builder pattern discovery + transform tolerance

Replaces the single `commit_artifact` tool with 8 builder tools that
mutate a run-scoped `discoveryDraft` incrementally. Each tool validates
its own args at call time — typo-suggestions via Levenshtein on inbox
field names, allowlists for master/cosmetics columns, transform/target
type compatibility, dead-rule detection. Agent self-corrects in the
same run on every tool_error instead of re-rolling a whole artifact.

DSL classify rules now structured args (`{signal, op, value}`) instead
of a quote-bracketed string — quoting bugs physically impossible. Split
transform is `transform="split", split_delim=","` — escaping bugs
physically impossible.

Transforms `numeric`, `int`, `ml_from_string`, `g_from_string` now
return `(nil, nil)` on empty/whitespace input. apply.applyOne treats
nil as "no value" and skips the rule for that row. Sephora's empty
`sale_price_usd` on not-on-sale items no longer kills apply.

### Alpha 0.9.3 — Bulk apply

Per-row writer paths (MatchOrCreateMaster, UpsertCosmetics, MergeTier3)
collapsed into UNNEST batches. applyOne now returns a `preparedApply`
struct with no DB writes. ApplyForTenant orchestrates 7-stage bulk
dispatch per inbox page:

  Stage 1: prepare every row (applyOne) — no DB.
  Stage 2: BulkMatchOrCreateMaster — 3 SQL stages per batch.
  Stage 3: split by wasCreated, accumulate cosmetics / tier3 /
           enrich / listings buckets.
  Stage 4-7: BulkUpsertCosmetics, BulkMergeTier3,
           EnrichExistingMaster, BulkUpsertListing, then MarkApplied.

Theoretical: ~10 DB roundtrips per 500-row batch instead of ~2000.
Reality: see "Bug 2" below.

This was the critical question. The artifact's cosmetics-branch
field_map (verified directly from `catalog.tenant_catalog_schema`):

```

tier3.secondary_category ← secondary_category   (Tier 3)
```

Owner's concern "may the agent just dump everything in Tier 3" — **no**.
Agent correctly used all three tiers exactly as the prompt directs:
universal facts in Tier 1, cosmetics-typed attributes in Tier 2,
Sephora-specific tail in Tier 3. The empty `master_cosmetics` is NOT
because the agent skipped Tier 2 — it's because the SQL adapter has a
bug (next section).

The 0.9.2 builder pattern + validators are doing what we asked: agent

## Bug 1 — `BulkUpsertCosmetics` SQL fails on nil slices

`apply_v2_bulk_cosmetics_failed` warning logged on every page of apply
(8 pages observed before stop). PostgreSQL error:
`cannot extract elements from a scalar (SQLSTATE 22023)`.

Root cause in `internal/adapters/postgres/catalog_v2_writer_adapter.go`:
the bulk insert marshals each cosmetics row as JSON, then SQL uses
`jsonb_array_elements_text(i.row->'skin_type')` to unpack array columns.
When `MasterCosmeticsUpsert.SkinType` is nil, `json.Marshal` emits
`null` — `jsonb_array_elements_text(null)` throws SQLSTATE 22023.

The per-row `UpsertCosmetics` doesn't hit this because it uses pgx
parameter coercion (`stringSliceArg`) which converts nil to an empty
text[]. The bulk path needs the same coercion BEFORE marshalling — set
nil array fields to `[]string{}` in the row map.

Apply continued past the failure (warning, not fatal). So master_products
+ tier3 + listings landed fine. Only `master_cosmetics` is empty.

## Bug 2 — Apply throughput ~700ms/row (NOT bulk speed)

Despite the 0.9.3 bulk pipeline, apply landed only 899 rows in 8 minutes.
That works out to ~700ms per row — basically the same as the per-row
pipeline before 0.9.3.

Suspected culprits, in priority order:
1. **MarkApplied is still per-row.** 899 × 70ms Neon roundtrip = ~60 sec
   just for marking. Need `BulkMarkApplied(itemIDs)`.
2. **BulkMatchOrCreateMaster's stage A query may be slow.** The
   3-key LEFT JOIN (LOWER(sku) OR gtin OR match_key) on
   master_products without a compound index can scan the whole table.
   Per-page 500-row batch could be doing a full table scan.
3. **All bulk stages run sequentially inside the page loop.** With
   Neon at ~70ms RTT and 5 stages per page × 17 pages = ~6 sec total
   for SQL alone — but real behaviour is much worse, so 1 and 2 dominate.

Fixes:
- Add `BulkMarkApplied` to InboxPort + adapter; remove the per-row
  loop in apply.
- EXPLAIN the BulkMatchOrCreateMaster stage A query against a 50k-row
  master_products table; if scanning, add a partial index or rewrite
  the JOIN into three smaller UNION-ALL JOINs each using its own index.
