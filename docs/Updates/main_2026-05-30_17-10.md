# Update — 2026-05-30 17:10 — v5 agent2 fail-open + data-derived `<fields>`

## Context
The deployed v5 pipeline (`v5-engine-production`) 500'd at agent2 for **every** tenant
with `ERROR: relation "catalog.field_definitions" does not exist (SQLSTATE 42P01)`.
Root cause: the `2026-05-14_catalog_flow_rebuild_part1.sql` migration dropped
`catalog.field_definitions` (mislabeled as "legacy staging"); the V4 migration that
created+seeded it was removed when V4 was dropped (commit 15ca2fe). Nothing recreates it.

The table is per-tenant render-vocabulary, read **only** to build agent2's `<fields>`
prompt block (`FormatFieldsBlock` → `ListFieldDefinitions`). Verified by code: data
binding (`engine.BindData`) is free-form `record[fieldBinding]` and never consults
field_definitions — so the table is best-effort **enrichment**, not a binding gate.
The 500 was a fail-CLOSED prompt-assembly path (agent1's digest cache is fail-OPEN).

## Approach (chosen with owner: fail-open + derive digest from data)
1. `ListFieldDefinitions` tolerates pg 42P01 (undefined_table) → returns empty + WARN,
   instead of erroring. Other SQL errors still propagate (fail loud for real problems).
2. `FormatFieldsBlock` is now fail-open (any list error → degrade + WARN) and builds the
   `<fields>` block from the **union** of published definitions + fields seen in the real
   sample data (`SampleFieldValues`), synthesising atom type/subtype/label for data-only
   fields. So a tenant/vertical with zero per-field config still gets a faithful vocabulary
   digest derived from its catalog — field_definitions becomes optional polish.
