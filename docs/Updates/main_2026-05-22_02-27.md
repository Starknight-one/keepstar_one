## What shipped

### A1 — Cosmetics nil-array fix + structural helper

`BulkUpsertCosmetics` was crashing on nil array fields (SQLSTATE 22023
from `jsonb_array_elements_text(null)`). Added `coerceStringSlice` helper
in `catalog_v2_writer_adapter.go` near the existing `stringSliceArg`.
All six array fields (`SkinType`, `Concern`, `KeyIngredients`,
`TargetArea`, `FreeFrom`, `Benefits`) now route through it before JSON
marshal — nil becomes `[]string{}` so SQL sees `[]` and lands empty
text[] in master_cosmetics.

The helper is general-purpose: any future Bulk* writer that JSON-marshals
array columns into a row blob can route through it and inherit the fix.

Test: `internal/integration_test/regression_cosmetics_nil_test.go`. Seeds
3 masters (2 all-nil, 1 mixed) and verifies columns land as empty arrays,
not NULL.

### A2 — BulkMarkApplied + LOWER(sku) index

Two parts to the apply-throughput fix:

1. `BulkMarkApplied(itemIDs []string)` added to `InboxPort` + adapter
   (UNNEST + `WHERE id = ANY($1)`). Replaced the per-row loop in
   `apply_v2.go:318-322` — was 60-70ms × N Neon roundtrips per page,
   now one statement.

2. Functional partial index `idx_master_products_lower_sku` on
   `LOWER(sku) WHERE sku IS NOT NULL AND sku <> ''` added to
   `catalog_migrations.go`. Without it, the 3-key cascade JOIN in
   `BulkMatchOrCreateMaster` was doing a full scan on every batch.

### A3 — Approve actually mutates columns

Per-field router landed in `curator/backend/internal/adapters/pending.go`.
`ApplyPendingChanges` now:

- Loads pending changes in one transaction (`FOR UPDATE`)
- Routes by `field_name`:
  - `tier3.<key>` → `master_products.tier3 || jsonb_build_object(...)`
  - cosmetics array col → `master_cosmetics` INSERT … ON CONFLICT with
    DISTINCT array union
  - cosmetics text/int col → `master_cosmetics` INSERT … ON CONFLICT with
    fill-when-empty / fill-when-null semantics
  - master_products text col → `master_products` UPDATE with
    fill-when-empty WHERE clause
  - unknown field → counted as skipped, no error
- Allowlisted column names (text/int/array maps in `pending.go`) — no SQL
  injection vector via field_name despite `fmt.Sprintf` in the templates

Handler at `handler_pending.go` now calls `ApplyPendingChanges` BEFORE
`BulkApproveMasters` + `BulkApprovePendingChanges` — so "approved" implies
"actually written".

Test: `curator/backend/internal/adapters/regression_pending_apply_test.go`
covers all five routing branches + a fill-when-empty no-op + the unknown
field skip. Has its own minimal `setupCuratorDB` / `seedCuratorTenant` /
`seedCuratorMaster` helpers because curator's adapter package had no
existing test infra.

### A4 — Idempotency lock-in

Surprise from exploration: `inbox_adapter.go:166-170` ALREADY implements
idempotency correctly. The `ON CONFLICT DO UPDATE` clause:

- Preserves `raw` and `applied_at` when `payload_hash` matches incoming
- Resets `applied_at = NULL` only on hash diff

So identical re-imports already skip apply (via `ListUnapplied` filter).
A4 in 0.9.4 is the regression test that locks this implicit contract in
so a future refactor of the upsert SQL can't silently break daily-cron's
idempotency guarantee.

Test: `regression_inbox_idempotency_test.go` seeds 3 rows, marks applied,
re-imports identical batch (asserts applied_at preserved), then
re-imports with one hash changed (asserts applied_at NULL for that one
only).

### B1 — Discovery patches existing artifact

`discovery_v2.go:runLoop` previously called `newDiscoveryDraft()` on every
trigger including `mapping_miss` and `unknown_vertical`. The agent had to
mentally reconstruct the existing artifact while patching one field — and
the existing artifact was silently overwritten on save.

After 0.9.4:

- New helper `newDiscoveryDraftFromArtifact(art)` in
  `discovery_v2_draft.go` — deep-copies branches + classify_rules from an
  existing `MappingArtifactV3` into a fresh draft (toolErrorCount reset).
- `runLoop` now: on `mapping_miss` / `unknown_vertical`, calls
  `d.artifact.Get(ctx, tenantID)` first; if an existing artifact comes
  back, seeds the draft from it via the helper. `first_install` and
  `manual` triggers still start empty (manual = explicit full re-discovery
  per the prompt's documented semantics).
- New action log entry `discovery_patch_from_existing` records when the
  draft was seeded from an existing artifact, with the branch + rule
  counts in the payload — gives us a trail when comparing pre/post
  artifact versions.

This unblocks Group B2 (schema-drift detection) where the "Apply
suggestion" button needs cheap patch-discovery rather than a full rebuild
on every drift finding.

**Test fallout** — `TestScenario_121and123_MappingMiss_ActionLogAndArtifactRefetch`
previously simulated an agent rebuilding the artifact from scratch in
the mock-response sequence. With B1 the draft is now pre-seeded with the
"bad" artifact under test, so the mock had to be patch-aware: it prepends
a `remove_field_mapping` call for the offending rule before the standard
commit sequence. Test passes; sc 121/123 still verify the
action_log+refetch contract.

Three new unit tests in `discovery_v2_draft_test.go`:
`TestDraft_FromArtifact_RoundTripsViaFinalize`,
`TestDraft_FromArtifact_NilArtifact_FallsBackToEmpty`,
`TestDraft_FromArtifact_DeepCopiesSlices`.
