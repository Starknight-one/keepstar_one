Цель: построить чистый шестишаговый поток данных и удалить всё что не работает.

## Архитектура (6 шагов)

```
[1] Источник            ← Shopify / CSV / Sheets / руками
       ↓
[2] Inbox               ← сырьё тенанта в JSONB, schema-agnostic
       ↓
[3] Mapping artifact    ← LLM-агент строит per-tenant файл маппинга
       ↓
[4] Каталог             ← тонкий master_products + slim listings + per-vertical mc
       ↓
[5] Обновления          ← webhook (≤1/день rate-limited) / sync now / mapping-miss
       ↓
[6] Удаление            ← soft-delete тенанта + cascade его данных
```

Принципы:
- **Inbox грязный** — это зона помоев, по нему не ищут. Никто кроме discovery agent и apply_v2 в него не лезет.
- **Маппинг эволюционирует от ошибок, не по расписанию.** При apply-фейле — узкий перезапуск агента с конкретной ошибкой на входе.
- **Vertical-typed storage**: `master_products` тонкий (Tier 1), vertical-specific поля идут в `master_cosmetics` (и потом другие per-vertical таблицы по мере появления новых тенантов). Это критично для V5 `BuildCatalogDigest` — дайджест читает компактный известный slice, не угадывая ключи в JSONB.
- **Fallback** для атрибутов без подходящей per-vertical таблицы → `master_products.tier3 JSONB`.
- **Webhook'и ≤1/день** на тенант + ручной триггер "Sync now".

## Откат

Все деструктивные операции в БД сделаны в одной транзакции. Точка восстановления — Neon point-in-time backup (TTL ~7 дней). Если что-то сломалось:

```bash
# git revert
git revert <commit-sha>

# psql restore from Neon time-travel: see Neon dashboard → Branches → Restore
```

Legacy Go-код жив и не вызывается напрямую новыми тестами — `git revert` SQL-миграции восстановит таблицы, и старый flow заработает (правда master_products колонки переменные обратно не восстановятся; их данные продублированы в master_cosmetics).
