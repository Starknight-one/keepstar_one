## Context

After chunks 6a (SDK adapter) and 6b (Agent2 + cache gate) the V5 chat-runtime worked end-to-end against live Anthropic + Neon, but only when invoked from a Go test. There was no HTTP entrypoint, the `visual_assembly` tool ignored the `ops` field the LLM was already trying to use, and the chunk-2 known race in `zoneWriteWithDelta` / `AddDelta` was still latent. This combined chunk closes all four.

After this chunk: a `curl POST localhost:8082/api/v1/pipeline` against the running V5 server returns a Document JSON; `visual_assembly` applies LLM ops on top of presets; state writes are tx-safe with retry on the unique-step race; and every adapter call records a span the request middleware can surface for `/debug/traces`-style waterfalls.

## Approach

**6c — HTTP layer**:
- `internal/config/config.go`: env var loader (PORT / DATABASE_URL / ANTHROPIC_API_KEY / LLM_MODEL / TENANT_SLUG / LOG_LEVEL). `MustLoad()` panics on missing required values so deployments fail loud at boot.
- `cmd/server/main.go`: real DI — config → JSON slog → DB connect → run all three migrations (state / preset / component) → adapters → ports → SDK client → tool registry + visual_assembly → prompt cache → Agent2Execute → handlers → middleware-wrapped router → http.Server with graceful shutdown via `signal.NotifyContext`.
- Three middleware (`internal/handlers/`): logging (request_id + slog + latency), CORS (open for chat widget), tenant (X-Tenant-Slug header → context, falls back to TENANT_SLUG env, validates via CatalogPort).
- Three handlers: session/init, session/{id}, pipeline.
- Routes wired with `net/http.ServeMux` method-specific patterns (Go 1.22+).
- Live HTTP integration test (`handler_pipeline_live_test.go`, `//go:build integration && live`) spins up the router via `httptest.NewServer` and walks /healthz → /session/init → /pipeline → /session/{id}. Hits real Haiku + real Neon. One run logs: `1 tool calls, 3524ms, cache_creation 4856 tokens, $0.00678`.

**6c — Ops applier**:
- `internal/engine/apply_ops.go`: `ApplyOps(doc, ops)` translates each JSON op into the matching `engine.Command` (`InsertCommand`, `UpdateCommand`, `DeleteCommand`, `MoveCommand`, `SetOverrideCommand` or `SetRootOverrideCommand`) and runs them via a fresh `CommandHistory`. Maintains a `$ref → node id` map across ops in one batch — when an op carries `"ref": "cta"`, later ops' `parent: "$cta"` rewrite to the actual id. `override` op heuristically picks descendant-shape vs root based on whether every prop value is itself a map.
- 10 unit tests cover insert / update / delete / move / ref-chain / fail-fast / override-root / override-descendant / missing-op / empty-list.
- Wired into `tool_visual_assembly.go`: pipeline order is now Materialise → ApplyOps → ExpandReplicates → ResolveAndInline → BindData. Ops run on the un-replicated tree so a single update lands on every replicate clone (V4 broadcast pattern). `parseOpsList` tolerates the two JSON shapes `[]interface{}` of maps and `[]map[string]any`.

**6d — Tx + retry**:
- `postgres_state.go`: `zoneWriteWithDelta` now wraps zone UPDATE + `addDeltaWithRetry` + state.step UPDATE in a single `pgx.Tx` (READ COMMITTED). Rollback on any error, commit on success. State and audit log can no longer diverge.
- Public `AddDelta` factored: `addDeltaOnce` runs the CTE INSERT against an executor (pool or tx); `addDeltaWithRetry` wraps with up to 3 attempts on SQLSTATE 23505 + 10-50ms randomised backoff. `isUniqueViolation` extracts the pgx error code via `errors.As`. Both pool and tx satisfy a small `pgExecutor` interface so the same SQL runs in either context.

**6d — Tracer**:
- `domain/span.go`: `Span` (Name + StartMs + EndMs + DurationMs + Detail), `SpanCollector` (concurrent-safe, anchored to time.Now() at construction), `WithSpanCollector`/`SpanFromContext` context helpers. V4-aligned — sorted by StartMs ASC then DurationMs DESC for waterfall ordering. Nil-safe pattern: caller checks `SpanFromContext(ctx)` once, skips Start when nil.
- 5 unit tests (basic, ordering, nil ctx, roundtrip, concurrent 50-goroutine load).
- Logging middleware now attaches a fresh `SpanCollector` per request and logs `span_count` at request end.
- Spans added: `postgres.GetState` / `UpdateData` / `UpdateTemplate` / `GetTenantBySlug` / `ListProducts` / `GetProduct` / `GetPublishedPreset` / `ListPublishedPresets` / `GetPublishedComponent` / `ListPublishedComponents`. Use cases: `agent2.execute` / `agent2.prompt` / `agent2.llm` / `agent2.tool.<name>`.
