## Context

Chunk 8 closed the trace upgrade. Re-reading V4 against V5 surfaced three
gaps that block any meaningful demo or prod swap, all in the LLM-facing
tool surface:

1. **`visual_assembly` was MORE constrained than V4.**
   `tool_visual_assembly.go:60` declared `"required": ["preset"]`. V4
   accepts three additional shapes: ops-only freestyle build (V4 prompt
   148-205), multi-widget composing for landings (V4 prompt 207-228),
   and ops-only modify on the existing tree. V5 today lacked all three.
2. **System preset library was 2 of expected 12.** The Agent2 prompt
   lists 12 presets (`agent2_prompt.go:51-65`); the DB only had
   `product_card` + `product_card_list_row` from chunk 5. Any LLM ask
   for `product_detail` or `empty_not_found` would error with
   «preset not found» and the conversation would stall.
3. **`tree_map` was advertised in the prompt but never computed.** Grep
   confirmed: every `tree_map` mention lived in prompts/comments; no
   producer in `usecases/`. Without it, modify-mode is broken
   architecturally — Agent2 doesn't know which node ids exist.

User decision in plan mode: include tree_map computation in this chunk
(option «do it right», 1-2h overhead, makes modify-mode actually
testable rather than a fiction).

After this chunk: Agent2 can call visual_assembly in any of three call
shapes; 7 new system presets back-stop the Agent2 catalog via an
in-process registry the postgres adapter consults on DB miss; tree_map
is built before every Agent2 turn that has a current Document and
injected as a `<formation_tree>` envelope into the user message. Live
HTTP test extended to four turns (initial / system-fallback /
multi-widget compose / ops-only modify) and runs green against Neon +
Anthropic Haiku.

## Approach

### Part A — tool surface

`internal/tools/tool_visual_assembly.go`:

- Dropped `preset` from `InputSchema.required`. Updated `Description`
  to enumerate the three call shapes.
- New branching in `Execute`:
  - **preset present**: original Materialise + components path; now
    also captures `preset.IsSystem` for the summary line.
  - **preset absent + state has Document**: load the persisted
    `state.Current.Template` as the starting `merged`. Mode upgraded
    from `freestyle` → `modify`. Lets ops target ids the LLM saw via
    tree_map.
  - **preset absent + no Document**: start from `engine.NewDocument()`.
    Freestyle build from primitives.
  - **both absent**: `ToolResult IsError` («either preset or ops or
    both must be provided»).
- Freestyle path with refs: lazy-load tenant components via
  `documentHasRefs` so an LLM-inserted ref still resolves.
- slog at exit-of-decision: `mode`, `preset`, `ops`, `replicate`,
  `system_preset`, `session_id`, `tenant` — flows through the chunk-8
  request_id middleware for trace correlation.

`internal/engine/apply_ops.go`:

- `resolveRef` now normalises `parent: "root"|"formation"|""` → `""`.
  V4 uses `"formation"` for document root inserts; V5's
  `op_insert.go:41` treats empty parentID as root. Without aliasing,
  the LLM emitting V4-style `"formation"` would error with «parent
  not found».
- New `TestApplyOpsParentAliases` covers all three aliases.

`internal/usecases/agent2_execute.go` (pre-existing bug surfaced
during multi-turn live testing):

- `historyLimit` trim was not pair-aware: trimming to the last 4
  messages could leave the prior list starting with a user
  `tool_result` whose matching `tool_use` had been dropped. The
  Anthropic API rejects orphaned `tool_result` blocks with
  «messages.0.content.0: unexpected `tool_use_id` found in
  `tool_result` blocks». New helper `isToolResultOnly` lets the trim
  step back one position when the cut would land on a tool-result
  orphan.

### Part C — tree_map computation

`internal/engine/tree_map.go` (new):

- `TreeMap` shape mirrors what the V5 prompt advertises (lines
  207-228 of `agent2_prompt.go` — TREE_MAP section): `preset_in_use`,
  `instances` (count + ids + shape.atoms), `literals` (top-level
  non-replicated frames), `components` (resolved ref bodies, deduped
  by ref name), `data_count`.
- `BuildTreeMap` walks a (replicated + resolved + bound) Document:
  - Groups top-level children by `__templateOrigin` (new attr stamped
    by `fanOut`); largest group becomes the primary `instances`,
    others become `literals`.
  - For each clone in the primary group: collects atoms via
    `collectAtoms`. Frames/groups recurse; resolved-component subtrees
    (carrying `__resolvedFrom`) emit a single ref-style row and stop.
  - Walks the document for `__resolvedFrom`-marked subtrees and emits
    one `TreeMapComponent` per unique ref name, listing the inner
    field bindings — components NEVER expose their ids in shape (those
    are shared across clones; targeting them would mutate every card
    at once).
- 5 unit tests (`tree_map_test.go`) covering: empty doc → nil,
  replicated cards, multi-widget compose, single non-replicated
  literal, resolved components.

`internal/engine/replicate.go`:

- `fanOut` stamps `__templateOrigin: <template id>` on each clone
  root. Lightweight cousin of V4's GroupID — sufficient for tree_map
  grouping (the full constraint-engine GroupID port stays deferred,
  see `v5-known-gaps.md`).

`internal/engine/component_resolver.go`:

- `expandRef` stamps `__resolvedFrom: <refTarget>` on resolved subtree
  roots. Inert at runtime (engine passes ignore the marker); enables
  tree_map to identify what came from which component without
  re-traversing the original ref structure.

`internal/usecases/agent2_execute.go`:

- New `buildFormationTreeBlock` round-trips
  `state.Current.Template` through `engine.Document` → `BuildTreeMap`
  → JSON, wraps in `<formation_tree>...</formation_tree>`.
- Called before every Agent2 turn that has a non-empty Template.
  Empty template → returns `""` → no envelope, no token cost.
- New `agent2.tree_map.build` span carries `size_bytes`,
  `data_count`, `components` attrs for cost-budget visibility.

Live measurement on chunk-9 turns (replicated card grid + freestyle
compose + ops-only modify): tree_map size ≈ 600-1500 bytes (≈
150-400 tokens). Well under the «turns into 20k cost» threshold the
user worried about; per-turn input-token impact is +3-7%.

### Part D — system preset registry

Architecture: **in-process `SystemPresetRegistry`** + DB fallback. NOT
per-tenant DB seeding. Reasons:

- Per-tenant seeding would force re-seeding on every new tenant and
  create implicit ownership confusion.
- System presets are by definition not tenant-specific — they're
  binary-shipped defaults. Tenants override per-name in v5_presets
  when they author via the future v9-canvas microservice.
- DB hits always win (the adapter consults DB first; registry fires
  only on `ErrPresetNotFound`).

7 new JSON files in `internal/engine/presets/seed/`:

- `product_card_compact.json` — small card, image-square, no rating
  ref, replicate:true.
- `product_card_horizontal.json` — image-left + info-right with
  description, brand, meta, replicate:true.
- `product_detail.json` — full detail (16:9 hero, title, price+rating
  row, brand badge, description), replicate:false.
- `product_detail_horizontal.json` — image-left detail, replicate:false.
- `text_explainer.json` — literal headline + body atoms (LLM passes
  ops to set content).
- `empty_not_found.json` — empty-state literal (default text).
- `error_generic.json` — error literal with alert wrapper.

`internal/engine/presets/presets.go`:

- `//go:embed` declarations for each new file.
- `SystemPresetSeeds map[string][]byte` — name → embedded body.
- `SystemPresetDefaultReplicate map[string]bool` — replicate metadata.

`internal/engine/presets/system_registry.go` (new):

- `SystemPresetRegistry` with `Get(name) ([]byte, bool)` + `List()
  []string` + `DefaultReplicate(name) bool`. Validates JSON on first
  hit; caches in `sync.Map`.
- 5 unit tests (`system_registry_test.go`) covering listing, every
  preset round-trips, cache hit, miss returns false, replicate
  metadata.

`internal/adapters/postgres/postgres_preset.go`:

- Added `systemRegistry *presets.SystemPresetRegistry` field +
  `NewPresetAdapterWithSystem` constructor (the bare
  `NewPresetAdapter` stays for tests of the raw DB path).
- `GetPublishedPreset` falls back to `systemPresetFallback(name)` on
  DB miss; wraps the registry payload as `*domain.Preset` with
  `IsSystem: true`.
- `ListPublishedPresets` unions DB + registry (DB rows win) and
  re-sorts by name.

`internal/domain/preset.go`:

- Added `IsSystem bool` field with `json:"isSystem,omitempty"` tag.
  No DB schema change — derived at adapter time.

`cmd/server/main.go` + the live test:

- Both wire `NewPresetAdapterWithSystem(pg, presets.NewSystemPresetRegistry())`
  so production and test share the same fallback path.

## Known gaps / caveats

- **tree_map cost optimisation** — current impl injects tree_map on
  every turn that has a non-empty template, even when the LLM is
  about to call a known preset (the preset's shape is already implicit
  in the system prompt). Vlad flagged this; deferred until first
  measured cost analysis. Optimisation: skip tree_map injection when
  the tool input ends up using a preset name (would require
  prediction or a follow-up cleanup turn). Logged as a new entry in
  `v5-known-gaps.md`.
- **GroupID full port still deferred** — `__templateOrigin` is the
  minimum surface tree_map needed; full V4 GroupID semantics
  (cross-widget constraints C1/C3) waits for the constraints chunk.
- **`mode=modify` slog label includes both true modify and freestyle-
  on-top-of-existing-template** (turn 3 in the live run was a
  multi-widget compose that the LLM laid on top of the
  product_detail from turn 2). The compose/modify distinction is
  semantic; the technical behaviour (start from existing doc,
  apply ops) is identical.
- **Modify-mode persistence across navigation** — V4 modifications
  persist when the user drills down + back. V5 today doesn't because
  navigation push/pop replay is stub (`state_reconstruct.go` rows
  documented in `v5-known-gaps.md`). P0-C territory.
- **System preset content quality** — the 7 new JSONs are minimal
  viable defaults. Brand colours / spacing / per-tenant overrides
  await canvas microservice (Stream B). Today they render reasonable
  shapes but not styled to a tenant's brand.
