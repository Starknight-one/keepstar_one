## Context

Chunk 4 shipped one inline preset and proved the pipeline glues end-to-end. What it did NOT prove: whether v5's headline architectural claim — "tenants edit reusable components in canvas, presets consume them via Ref" — actually works once you ask one component to serve more than one preset.

This chunk falsifies the claim by building the smallest non-trivial reuse: two components (`price_rating`, `brand_badge`), two presets (`product_card`, `product_card_list_row`) that both consume them, and a pipeline pass that takes preset+components+data and produces correctly bound trees per preset. If reuse couldn't survive the replicate × component-expansion combo, we'd find out cheaply now rather than expensively under chunk-6 LLM load.

User-confirmed direction: future canvas microservice will write to the V5 tables we just shipped, so this schema is final, not a stopgap.

Plan: `docs/Updates/v5/plans/chunk-5-micropresets.md`.

## Approach

Verbatim execution of the approved plan with one bug surfaced and fixed mid-flight.

**The bug.** `cloneNode(source)` inside `ComponentResolver.expandRef` deep-copies the source component, including the `reusable:true` flag that `Materialise` stamped on the component definition. Without intervention, the resolved instance subtree carries the marker too — and chunk-5's new `BindData` skip-rule then ignores the entire instance, leaving every price/rating/brand atom unbound. First e2e run reproduced this exactly: clones lacked all ref-sourced bindings.

**Fix.** `ResolveAndInline`, when expansion succeeds, deletes the `reusable` key on `resolved.Root` before splicing the instance into place. Justification lives in code: `reusable` is only ever stamped on the component-definition root by `Materialise`, never on descendants, so a single delete is sufficient. Added a regression test (`TestResolveAndInlineStripsReusableFromInstances`) and updated the corresponding gap-registry row to spell out the asymmetry: definitions retain the marker, instances don't.

**Pipeline order.** Reaffirmed: `Materialise → ExpandReplicates → ResolveAndInline → BindData`. Replicate runs before component expansion so each replicated card retains its own ref pointers + dataIndex; the resolver then expands each cloned ref independently. dataIndex inheritance survives the chain because the cloned card root carries `dataIndex:i` and the binding walker threads it down through the resolved subtrees.

**Adapter discipline.** `resolveTenantID`+`isUUID` were sitting inside `postgres_preset.go` from chunk 4; chunk 5 needs them again for the component adapter, so they moved to `tenant_resolve.go`. Both adapters now share the helper. No behaviour change.

**Seeds.** `product_card` was refactored in place — hero + title remain inline, price/rating/brand became RefNodes pointing at the new components. `product_card_list_row` is a new file; row layout, adds a `description` atom unique to this variant, otherwise reuses the same two components. Both round-trip-validated by `presets_test.go`.

## Known gaps / caveats

All registered in `docs/v5-known-gaps.md`:

- **Multi-root components** — `Materialise` only consumes `Document.Children[0]` from each component. One-root is the natural shape; multi-root would need either component packs or a separate materialise mode.
- **ID collisions across components** — `Materialise` has no dedup; if two components define a node with the same id, `FindNodeByID` returns whichever is appended first. Today's seeds use deterministically-distinct IDs (`price-rating-root`, `brand-badge-root`).
- **`ResolveAndInline` doesn't mint fresh IDs on resolved subtrees** — descendants of two ref expansions of the same component share IDs (only the resolved root is unique because `expandRef` forces it to the refNode's id). Inner-id collisions only matter for path-deep ops, which V5 doesn't support yet.
- **`BindData` skip semantics asymmetry** — top-level definitions retain `reusable:true` (skipped); instance roots strip it on resolution (walked). Documented for clarity.
- **Closed**: catalog adapter gap (shipped in chunk 3, exercised in chunk 4 e2e).
- **Pushed to chunk 6**: Agent2 prompt-builder with `<fields>` block — natural pair with the first real Agent2 turn once the Anthropic adapter, HTTP server, and tracer ports land.

What to watch in next chunks:
- **Chunk 6 (LLM in the loop)** — when the prompt-builder lists atom IDs from a refactored preset, it must show the *consumer-side* RefNode IDs (`card-meta`, `row-meta`) rather than the *component-internal* atom IDs (`pr-price`, `pr-rating`). The latter would be wrong for two reasons: they're shared across instances (post-resolve they all collide), and they're not what the LLM should reason about (the LLM moves Refs around, not their innards).
- **First token measurement** lands when chunk 6 wires Anthropic and we run a real Agent2 turn over `product_card` vs V4's same scenario. Architecture is now ready; behaviour is the test.
