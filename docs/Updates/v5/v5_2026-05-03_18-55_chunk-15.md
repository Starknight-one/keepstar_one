## Approach

### 1. Prompt suite

`scripts/v5-smoke-prompts.json` — 25 prompts × 5 тэгов (search 8,
drill 4, modify 5, compose 4, edge 4). Mixed RU + EN — реалистично для
hey-babes-cosmetics.

### 2. Bash + Python runner

`scripts/v5-smoke.sh` — bash оркестрация + inline Python для JSON
обработки и summary.md рендера. Логика на каждый prompt:
- POST V5 `/api/v1/pipeline` → save full response, capture wall-clock
- POST V4 `/api/v1/pipeline` → save full response, capture wall-clock
- GET V4 `/debug/traces/?format=json` → найти match по `sessionId` +
  `query`, save trace JSON. Это **единственный способ** достать V4
  cost/tokens/cache из public API — V4 pipeline endpoint не
  экспонирует usage.

V4 trace JSON использует короткие имена `cacheRead` / `cacheWrite`
(не `cacheReadInputTokens` как V5). Первая итерация скрипта искала
длинные → нули. Fixed; перерендерил summary.md из уже сохранённых
trace-JSON'ов без повторного хождения в API (экономия $0.25).

### 3. Output structure

`docs/v5-smoke/2026-05-03_18-47/`:
- `summary.md` — committed
- `prompts.json`, `meta.json` — committed (snapshot of input + run
  context)
- `pNN.v5.json`, `pNN.v4.json`, `pNN.v4.trace.json` — gitignored
  (`docs/v5-smoke/**/p*.json`), local-only review

|---|---|---|---|

| Latency p50 | 8166ms | 2608ms | **+213%** |

V5 ~3× медленнее V4 на p50, ~2× на p95. Token efficiency лучше у V5
(-24% input через tree_map), но output tokens на compose-промптах
большой (e.g. p19 «landing page» V5 emits 929 output tokens). Cost
сопоставимо: +10% V5 vs V4. Both backends каэшируют примерно одинаково.

## Known gaps / caveats

- **V4 cost — in-memory metricsStore.** `/debug/traces` отдаёт только
  что висит в RAM на V4. Если V4 рестартанётся — старые traces
  потеряны. На prod без user traffic это не проблема для smoke.
- **Quality assessment вручную.** V4 эмитит Formation, V5 —
  scene-graph Document; разные структуры, auto-diff requires
  schema-aware comparator. Vlad листает per-prompt JSON dumps своими
  глазами.
- **Anthropic cache state.** V5 cache_read зависит от того
  кэширован ли prefix. Этот run был «warm» (после chunk 14 deploy +
  предыдущие smokes). На полностью cold start V5 latency могла бы
  быть выше.
- **Smoke ran from MacBook → Railway prod**, не Railway-internal.
  Сравнение из per-prompt JSON: V5 server-reported `latencyMs` 7939ms
  vs V5 client wall-clock 9310ms на p01 → **client overhead ≈ 1.4s
  per request** (TLS handshake + Mac↔europe-west4 RTT). То есть
  заявленные «V5 8s p50» — это server-side, **не** localhost-артефакт.
  Bottleneck — V5→Anthropic 2 sequential LLM calls. Для clean
  Railway-internal baseline нужен smoke с другого сервиса в том же
  проекте (`railway run --service curator bash scripts/v5-smoke.sh`
  или временный smoke-runner сервис) — **отдельный chunk** если
  понадобятся точные prod-region numbers.
- **One tenant only**: `hey-babes-cosmetics`. Multi-tenant smoke —
  отдельный chunk если появятся реальные тенанты.
- **Per-prompt JSON dumps локально.** Vlad'ом для quality review;
  если он хочет их в git — переключить gitignore rule.

## Quality comparison V5 vs V4 (sample dive)

Я разобрал 8 представительных prompts из per-prompt JSON dumps —
short take по каждому:

| # | prompt | V5 | V4 | Кто лучше |
|---|---|---|---|---|
| p01 | «покажи 3 продукта» | frame 3ch wrap (3 product cards) | `mode=single 1w "Ничего не найдено"` (no tool call!) | **V5** clear win — V4 даже catalog_search не вызвал |
| p06 | «новинки» | frame 3ch (3 cards) | grid 50w (DUMPS ALL 50 PRODUCTS) | **V5** — V4 заваливает экран |
| p09 | «открой первый» | frame 2ch (re-search, не drill) | grid 50w (тоже не drill) | **Tie** — оба не справились с drill (нет prior products) |
| p13 | «сделай заголовок красным» | frame 4ch (modify-mode applied) | mode=single 1w 8 atoms | **Tie** — оба что-то применили |
| p18 | «сделай лендинг с продуктами» | frame 1ch wrap (composed) | grid 12w | **V4** показал больше деталей; V5 сжал |
| p20 | «карточка крупно + остальные мелко» | 3 frames (hero + cards + extra) | **0 widgets** (ничего не нарисовал!) | **V5** clear win — V4 fail |
| p22 | «квантовые компьютеры» | empty_not_found preset (graceful) | grid 50w (snowboard spam!) | **V5** clear win — V4 показывает мусор на empty match |
| p25 | «привет» | frame 3ch (greeting card) | **0 widgets** | **V5** clear win — V4 не обрабатывает greeting |

**Pattern**: V5 эмитит **структурированный intentional output** (правильный
preset под intent: empty_not_found, product_card replicate, composed
frames). V4 либо **дампит сырой grid 50 widgets** (без фильтра), либо
**показывает 0 widgets** (на compose / greeting). На «нормальных»
search-промптах V4 быстрее и часто адекватнее, но edge cases / compose
он валит, а V5 нет.

**Net**: V5 latency 3× хуже, но quality на edge cases и compose
заметно лучше. V4 быстрее на pure-search, но квазидетерминированно
плохо ведёт себя на «гибких» запросах. Это два разных продуктовых
профиля.

## Post-run discovery: latency was geographic, not architectural

После того как смоук был зафиксирован в `summary.md`, Vlad обратил
внимание что **V5 крутился в Singapore** Railway region (видно в
service settings), а Anthropic API + Neon DB живут в **us-east-1**.
Каждый LLM call и каждый Postgres-query из V5 уезжал транс-Тихоокеанским
hop'ом (~150-200ms RTT × несколько roundtrips на каждый call).

Vlad перенёс v5-engine в US region. Сразу после redeploy одна serial
проверка с моей машины:

| run | latencyMs | a1Ms | a2Ms | wall-clock | cache_read |
|---|---|---|---|---|---|
| cold (1st turn) «покажи 3 продукта» | 3446ms | 2391 | 1055 | 3894 | 0 |
| warm 1: «тонер для жирной кожи» | 2423ms | 1350 | 1073 | 3197 | 7546 |
| warm 2: «сделай заголовок красным» | 1984ms | 1190 | 794 | 2438 | 7546 |
| warm 3: «покажи 3 продукта» | 1881ms | 1045 | 835 | 2642 | 7546 |

**V5 warm cache latency теперь ~2000ms** — конкурентно с V4
(п50=2608ms в исходном смоуке). Cold cache ~3500ms.

**Вывод**: «V5 в 3× медленнее V4» **не было архитектурным ограничением**,
а было региональным просчётом конфига. После переезда V5 в US gap
закрылся почти полностью — V5 ~равен V4 на warm cache, чуть медленнее
на cold. Это **меняет recommendation для chunk 16** ниже.

## Recommendation для chunk 16

После переезда V5 в US latency **больше не является блокером для swap**
— V5 warm cache ≈ V4 на ~2000ms p50. Quality на edge cases / compose
у V5 объективно лучше (см. секцию выше).

Кандидаты на следующий chunk (приоритет за Vlad'ом):

1. **Frontend route swap behind flag** (item 13). Под флагом
   переключаем V5 на одного-двух tenants для opt-in beta. Quality +
   steady-state speed валидируем на реальных запросах. Ближайший
   практический шаг — V5 ready.

2. **Skip Agent2 LLM call когда Agent1 = «no-op»** — оптимизация
   обозначенная Vlad'ом. V4 уже делает это (Agent2.llmMs=0 на «no
   data change»). Ускорит drill/modify/greeting на ~1s каждый. Не
   срочно — V5 уже в приемлемом latency-окне.

3. **Re-run smoke after region migration** — для записи canonical
   baseline. ~3-4 минуты, ~$0.30. Заменит Singapore-числа в
   `docs/v5-smoke/2026-05-03_18-47/summary.md` на US-числа.

4. **Railway-internal smoke** — отдельный smoke-сервис в том же
   регионе для **точных** Railway-side numbers без TLS handshake
   noise. Не блокер, по требованию.
