# Chunk 3 — port V4 binding layer to V5 scene-graph

**Branch**: v5
**Date (UTC)**: 2026-05-02 16:53
**Commit**: 524d6c3
**Parent**: 599b4b7

## Context

After chunks 1-2 (engine + sectional state) the chat had an engine and a
state model but no way to fill atom values from per-record data — no bridge
from "Agent1 loaded N products" to "atoms in the scene-graph carry the
right name/price/brand". Without that bridge, the LLM has to spell out
every value in tool-call arguments, which is the V4-vs-naïve token cliff.

This chunk ports V4's binding mechanism to V5 with three deliberate
adaptations driven by deep-dive research (3 parallel Explore agents read
the V4 code and wrote up findings — captured in
`docs/Updates/v5/plans/chunk-3-binding.md` Context section):

1. Vlad's correction took: V4 binding is **not** a fixed slot vocabulary,
   it's arbitrary `fieldName` lookup. V5 keeps it that way as
   `fieldBinding` attribute on scene-graph nodes.
2. **ProductToMap precedence reversed**: Typed > Tier2 > Extra (was
   Typed > Extra > Tier2 in V4). Aligns with the DB-side merge_apply
   rule (`tier2 || EXCLUDED.tier2`) — curator wins over raw vendor data.
3. **Honest `__bound` flag** closes V4 Грабля #1 (empty cards marked
   "bound" → LLM never filled them).

## Approach

Verbatim port of FieldDefinitionPort + adapter (heybabes-style PIM samples
+ test-electronics Extra spread). CatalogPort cut to a read-only subset (5
methods → 3 here: GetTenantBySlug, ListProducts, GetProduct) — vector
search and write side stay in admin/curator and are not V5's concern.

`BindData` is a fresh implementation for scene-graph (V4's was for
Formation/Widget/Atom). Walks `Document.Children` recursively (using chunk
1's `Children`/`SetChildren` helpers so `[]Node` and post-Unmarshal `[]any`
both work), and per node:

- No `fieldBinding` → skip (literal LLM-text in `content` survives).
- `fieldBinding` present → resolve `data[dataIndex|0][fieldBinding]`.
- Hit → write to `content` (TextNode) or `value` fallback, set
  `__bound: true`.
- Miss → register in `BindResult.Missing`, do NOT set `__bound` (the
  Грабля #1 fix).

`ServiceToMap` rounds out service-side parity. Service binding precedence
is just Typed > Attributes > Extra — services have no Tier2.

V4 bugs ported as-is in chunks 1-2 stay logged in `docs/v5-known-gaps.md`;
none of them are touched here (LLM-text/binding decoupling does not
intersect with delta-stream tx semantics).

## Known gaps / caveats

- **Image binding deferred** — chunk 3 binds TextNode to `content` and
  everything else to a generic `value` key. Image-fill binding
  (`fills[0].image`) lands in chunk 4 alongside the first real preset.
- **Replication itself stays in chunk 4** — chunk 3 only consumes the
  `dataIndex` marker. Building an op that clones a RefNode subtree per
  data record (and stamps `dataIndex` on each clone) is chunk-4 work.
- **CatalogPort cut to read subset** — VectorSearch, ListServices,
  GetService not ported. Service binding works via `ServiceToMap`, so
  whenever Agent1 loads services into state we just need to add the read
  methods. Defer until a service preset shows up (chunk 5).
- **`<fields>` block not yet in any prompt** — `FieldDefinitionPort` is
  ready, but the Agent2 promptbuilder that consumes it is chunk 4.
- **`meta.Fields` data-shape bug from V4** — the V4 catalog search picks
  fields from the first product instead of `field_definitions`. We
  haven't ported catalog search yet; when we do (chunk 6), the fix is
  to pull `field_definitions` for the tenant and merge with populated
  fields from the result set.
